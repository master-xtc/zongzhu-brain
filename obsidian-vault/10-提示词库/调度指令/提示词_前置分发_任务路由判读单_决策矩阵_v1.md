# 提示词 · 前置分发路由（任务判读单 + 决策矩阵）

## 基本信息
- 用途：接任何新任务时先走"判读—路由—派单"，把任务自动分派到提示词库/skills/下属中最合适的执行资源；总助不硬扛、不重复造轮子
- 适用场景：所有新任务开工前（建站/落地页/后台/H5/商品页/文案/图像/视频分析/小说/复盘/调度）；也用于对客户的需求收集与报价
- 版本/日期：v1.0 / 2026-08-14（方法论来源：视频二《UI工作流Skill前置路由分发》，迁移到习总 AI 员工体系）

## 变量位（使用时替换）
- {任务描述}：习总或客户的原始需求（原文粘贴，不加工）
- {任务类型}：落地页 / 品牌站 / 后台 / 商品页 / H5 / 长文案 / 短视频脚本 / 视频分析 / 海报 / 小说章节 / 复盘 / 其他
- {输出目录}：当前窗口主目录（D 盘规范）
- {可用资源}：提示词库六类 + growth\skills + 豆包(ark) / DeepSeek / Hermes / WorkBuddy / Claude

## 正文模板

### 第一步：判读单（先给猜测，习总/客户点头确认，不对就改）
| 字段 | 含义 | 本任务猜测 |
| --- | --- | --- |
| brand | 是品牌/门面页吗？ | （如：是/否） |
| register | 有注册/转化目标吗？ | （如：无，纯展示） |
| mobile_only | 只在手机上看吗？ | （如：否，双端） |
| lifespan | 要活多久（一次性/长期）？ | （如：长期，3个月后还要改） |
| existing | 有旧站/旧版吗？ | （如：无，从零） |
| weight | 要快还是要质感？ | （如：要质感，当门面） |

### 第二步：5 问题决策树（每问切掉一批候选，无关问题直接跳过）
1. 给谁看？（C端大众 / 客户决策人 / 内部后台）→ 决定审美路线：C端走品牌质感，后台走信息密度
2. 生命周期？（一次性活动 / 长期运营）→ 决定要不要上组件规范（长期必上）
3. 平台？（桌面 / 移动 / 双端）→ 决定断点与触控策略
4. 规模？（单页 / 多页）→ 决定要不要页面骨架模板
5. 优先级？（速度 / 质感）→ 决定执行资源与简化范围

### 第四步：四操作治理（按需选用）
- update：判读单改一个字段 → 路线自动重算
- combine：任务按层拆开，多资源各管一段（如：豆包出图 + DeepSeek 文案 + 总助整合）
- compare：两个方案各出一版，对比后选优（时间翻倍，拿不准才用）
- audit：交付时附判读依据与字段来源（"哪些是客户确认、哪些是猜测"），客户可溯源

### 第五步：派单五要素（下发执行资源时必含）
目标（一句话）→ 背景（为什么做）→ 约束（审美规范/红线/命名）→ 交付物形式（路径/格式）→ 验收标准（程序化证据或豆包 vision 复核）+ 截止要求

### 第六步：验收
- 文本/代码任务：程序化证据链（token 命中 / DOM 计算样式 / 像素采样），不主观断言
- 视觉/图像任务：豆包 vision 复核（红线：总助不假装看图）
- 交付前检查：文件落窗口主目录、命名规范、无隐私泄露、图文一一对应

## 变体
1. 变体A（建站接单）：判读单直接面向客户，六字段+猜测式确认=专业需求收集，报价一次到位（可附 audit 作差异化交付物）
2. 变体B（内容量产）：先判"单条标准模板"，再批量复制执行，避免逐条自由发挥
3. 变体C（技术分析）：GitHub API 核实真实性 + 程序化核验优先，口播数据不直接采信
4. 变体D（小说写作）：判读单改字段（平台/连载长度/风格基调），路由到小说写作提示词

## 验收标准
- 每个新任务开工前先跑判读单，路由结论写进任务文档
- 覆盖矩阵内每个任务类型都有明确"主/补/验"资源，无资源时如实上报不硬扛
- 判读单每项都有"猜测+依据"，客户确认的与猜的明确区分
- 交付汇报末尾附能力自查结论 + 所用路径
